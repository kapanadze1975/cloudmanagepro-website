Part 1 — Create Intune device compliance policies (step‑by‑step)

Overview

Intune compliance policies define the device health and configuration requirements that determine a device’s compliance state. Conditional Access uses that compliance state as a signal to grant or block access. Follow the documented guidance to create and monitor policies. (See Microsoft Intune: Create a compliance policy and fundamentals deployment steps in References.)

Exact navigation (Endpoint Manager)

Microsoft Intune admin center (Endpoint Manager):
Microsoft Intune admin center → Devices → Compliance policies → Policies → Create policy

Step 1 — Start a new compliance policy

  1. In Microsoft Intune admin center navigate: Devices → Compliance policies → Policies → Create policy.
  2. Platform: Choose the target platform (e.g., Windows 10 and later) as documented.
  3. Profile type: Select the policy type appropriate for the platform (the portal will show available settings per platform).

Step 2 — Configure core Windows settings (recommended example)

Use the documented Windows settings reference when configuring platform‑specific options. Example recommended configuration (values shown as example starting points — adapt to your organization’s security posture and user impact):

  • Minimum OS version: Windows 10 21H2 (or your chosen minimum). Rationale: ensures security updates and feature parity for compliance checks.
  • Require BitLocker / device encryption: Yes (Require encryption). Rationale: protects data at rest.
  • Defender/AV requirement: Microsoft Defender Antivirus running and up to date (or equivalent realtime protection). Rationale: ensures antimalware coverage.
  • Secure Boot: Require Secure Boot enabled. Rationale: reduces firmware/boot‑level tampering.
  • Password rules: Require device password/PIN with complexity and minimum length (example: minimum 6 characters / alphanumeric or PIN per your policy). Rationale: prevents easy local access.

Notes and cautions for these settings:

  • Verify minimum OS and encryption requirements against your device fleet — too strict a minimum can mark many devices noncompliant.
  • Requiring BitLocker or Secure Boot may prevent access for devices that cannot support those features (legacy hardware). Consider phased rollout.
  • Account for shared devices, kiosk devices, or line‑of‑business devices that might need exemptions or separate policies.

Step 3 — Cross‑platform basics (Android / iOS / macOS)

  1. Create separate policies per platform where the available settings and controls differ.
  2. For cross‑platform basics, include:
    • Minimum OS version per platform.
    • Device encryption requirement where supported.
    • Device health / threat protection (where available).
    • Required PIN/password complexity.
  3. Apply platform‑appropriate settings documented in the Intune Windows settings reference and compliance policy creation guidance.

Step 4 — Assign the policy

  1. After configuring settings, assign the policy to user or device groups as appropriate.
  2. Use targeted pilot rings (a small group first) before broad production assignment.

Step 5 — Monitor the policy

Navigation for monitoring (Endpoint Manager): Microsoft Intune admin center → Devices → Monitor → Compliance policies (or from Compliance policies → select a policy → Monitor)

Use the monitored reports to view compliant/noncompliant counts and per‑device state as documented in the Intune monitoring guidance.

Part 2 — Create an Entra Conditional Access policy requiring device compliance

Overview

Conditional Access policies in Entra evaluate signals like user, device compliance, location, application, and risk to enforce access controls. You can require that devices are marked compliant by Intune before granting access to Microsoft 365 apps. Refer to the Conditional Access policy documentation and policy examples in References.

Exact navigation (Entra admin center)

Entra admin center: Entra admin center → Identity → Conditional Access → Policies → New policy

Step 1 — Create a new Conditional Access policy

  1. In Entra admin center navigate: Identity → Conditional Access → Policies → New policy.
  2. Name the policy clearly (example: “Require Intune device compliance for Microsoft 365”).

Step 2 — Assign users and groups

  1. Under Assignments → Users and groups, choose the user groups this policy targets. Best practice: start with a pilot group before enabling for all users.
  2. IMPORTANT: Exclude break‑glass emergency accounts (global admins or a small emergency access group) from the policy to avoid lockout. The Entra Conditional Access guidance explicitly highlights careful management of emergency access accounts.

Step 3 — Cloud apps or actions

  1. Under Assignments → Cloud apps or actions, select the Microsoft 365 apps you want protected (for example Exchange Online, SharePoint Online, Microsoft Teams, and Office 365 apps).
  2. Use documented guidance to select applications appropriately.

Step 4 — Conditions (optional)

Optionally add conditions (locations, device platform, client apps) per your needs.

Step 5 — Access controls — Require device compliance

Under Access controls → Grant → select “Require device to be marked as compliant” (the documented control). This uses the Intune compliance signal.

You may combine controls (for example, require compliant device OR require approved client app) depending on your scenario.

Step 6 — Enable policy safely (report-only/testing)

  1. Initially set the policy to “Report-only” or use a pilot group to observe impact without blocking sign‑ins.
  2. After verifying behavior, enable the policy in “On” mode.
  3. Documentation examples and best practices show testing first to prevent unexpected user disruption.

Part 3 — Recommended settings, rationale, and cautions

Recommended example configuration summary (start points — modify to your environment):

  • Minimum OS:
    • Windows: Windows 10/11 build baseline as your organizational minimum.
    • macOS/iOS/Android: set platform-appropriate minimum versions.
  • Encryption: Require device encryption (BitLocker on Windows / FileVault on macOS / platform‑equivalent).
  • Defender/Antivirus: Require Microsoft Defender or equivalent realtime antimalware where supported.
  • Secure Boot: Require for Windows devices where hardware supports it.
  • Password/PIN: Minimum complexity and length appropriate to your policy.
  • Break‑glass accounts: Exclude emergency access accounts from Conditional Access policies.
  • Testing: Use report‑only mode or a small pilot group before full enforcement.

Rationale and cautions

Rationale: Device compliance policies provide a consistent device state signal for Conditional Access to reduce risk and enforce organization policy for Microsoft 365 access.

Caution: Aggressive requirements (higher OS minimums, mandatory Secure Boot or BitLocker) can immediately mark existing devices noncompliant. Use phased deployment and pilot testing.

Caution — break‑glass accounts: Always maintain at least one or two emergency access accounts excluded from restrictive Conditional Access policies to prevent accidental global admin lockout.

Part 4 — Troubleshooting checklist and remediation steps

Where to view compliance state and policy evaluation

Intune device compliance state: Microsoft Intune admin center → Devices → All devices (select device) → Overview or Device compliance details (Also: Devices → Compliance policies → select policy → Monitor). Use these views to see per‑device compliance and noncompliant settings as reported by Intune.

Conditional Access sign‑in and evaluation reason: Entra admin center → Identity → Conditional Access → Insights and reporting (and Sign‑in logs via Azure AD sign‑in logs) to see why a sign‑in was allowed or blocked. Use sign‑in logs to view Conditional Access policy evaluation and the reason for grant/deny decisions.

Common causes of noncompliance

  • Device not enrolled or not reporting to Intune.
  • Device has outdated OS below the minimum version set in the policy.
  • Encryption (BitLocker/FileVault) not enabled or not reporting.
  • Antimalware not installed, not running, or not reporting.
  • Secure Boot disabled on hardware.
  • Device not checked in or missing recent sync.

How to force a device sync / check‑in

Common approaches:

  • On Windows devices, users can open Settings → Accounts → Access work or school → select the work account → Info → Sync (device sync action depends on platform and enrollment method).
  • Company Portal app (where used): open the Company Portal app and use “Sync” or “Check for updates” to force device check‑in.

Sample remediation steps

  1. Identify noncompliant devices in Intune (Devices → Compliance policies → noncompliant devices).
  2. Review the noncompliant reasons on the device details page.
  3. For each reason:
    • OS version: schedule or push updates, check update deployment tools.
    • Encryption: enable BitLocker/FileVault on the device or provide instructions for users; validate TPM presence and recovery key storage.
    • Defender/AV: ensure Microsoft Defender or approved AV is installed, up to date, and reporting.
    • Secure Boot: instruct users or manage firmware settings for devices that support Secure Boot.
  4. Force a device sync (Company Portal or device settings) and re‑check compliance.
  5. If Conditional Access blocks sign‑ins and you used report‑only testing, review sign‑in logs to confirm expected behavior. If policy is enforced and blocking unintended users, consider temporarily excluding affected users while remediation proceeds.

Troubleshooting checklist (quick)

  • Is the device enrolled in Intune? Yes/No.
  • Has the device checked in since settings changed? If not, force a sync.
  • Does the device report the specific failing setting (OS version, encryption, AV, Secure Boot)? Check device details in Intune.
  • Are users experiencing Conditional Access blocks? Check Entra sign‑in logs for policy evaluation details.
  • Are emergency/break‑glass accounts excluded? Confirm to avoid admin lockout.

Part 5 — Licensing callout

Conditional Access requires appropriate Entra licensing. As documented, Conditional Access features are included with Entra ID P1 or equivalent SKUs. Ensure your tenant license includes the required Entra Conditional Access capability before enforcing device compliance-based Conditional Access policies.

FAQ

  1. What is an Intune device compliance policy?

    An Intune device compliance policy defines the device configuration, health, and security requirements (for example minimum OS version, encryption, antivirus state) that Intune evaluates to mark a device as compliant or noncompliant.

  2. How does Conditional Access use Intune device compliance?

    Entra Conditional Access evaluates the Intune compliance signal and can require that a device is marked compliant before granting access to Microsoft 365 apps. This enforcement is configured in Conditional Access grant controls by selecting “Require device to be marked as compliant.”

  3. How can I test a Conditional Access policy without blocking users?

    Use report‑only mode or apply the policy to a small pilot group first. Review sign‑in logs and Conditional Access reporting to validate behavior before enabling enforcement for all users.

  4. What should I do if users get locked out after enabling a Conditional Access policy?

    Ensure you have excluded emergency (break‑glass) accounts from the policy. If unintended users are blocked, temporarily exclude affected accounts/groups while you remediate device noncompliance and then re‑enable the policy.

  5. What licensing do I need to enforce Conditional Access based on device compliance?

    Conditional Access requires Entra ID P1 or equivalent licensing; verify tenant licensing before enforcing policies.
